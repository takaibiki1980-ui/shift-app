### ④ 実装した計算式（案A 逆数加算方式）

```javascript
// P12: 遷移確率適合ペナルティ（Phase5 Step6-B）
// transitionRate[prev][curr] が低い（珍しい遷移）ほどペナルティが大きくなる。
// rate が null（データなし遷移）はスキップ。P10/P11 と同形の逆数加算方式。
const TRANS_WEIGHT = 25;
if (trendKeys.length > 0) {
  for (const s of ds) {
    const tKey = trendKeys.find(k => nameMatch(k, s.name));
    const trend = tKey ? shiftTrend[tKey] : null;
    if (!trend?.transitionRate) continue;
    for (let d = 2; d <= days; d++) {
      const prev = res[s.id]?.[d - 1], curr = res[s.id]?.[d];
      if (!prev || !curr) continue;
      const rate = trend.transitionRate[prev]?.[curr];
      if (rate != null) score += (1 - rate) * TRANS_WEIGHT;
    }
  }
}
```

### ⑪ 実装を採用すべきか（実測値のみで判断）

**不採用**。

理由（実測値のみ）:

1. **採用試行インデックスが変化したのは 1〜2%** — 100試行中 1〜2回しか別の試行を選ばなかった。P12 は trial 選択にほぼ影響しない。

2. **shortage・公休違反・連勤違反・syncRate いずれも有意差なし** — 追加する意義が実測で確認できない。

3. **score値が恒常的に +3,900〜+4,000 膨張** — 試行の品質は変わらないのに評価値だけが大きくなる。将来の比較・デバッグ基準を狂わせる副作用がある。

4. **採用試行変化がない理由（構造的）**: shortage（P4）が支配的（約 17〜18 コマ/trial）なため、P4 の点数規模（shortage 1コマ = 300〜1,000点）が P12 の最大ペナルティ（270件×25点=6,750点）を完全に吸収してしまう。全 30試行が同程度の P12 点を受けるため差が出ない。

---

### ⑫ 次に進むべきか、元へ戻すべきか

**元へ戻す（revert）**。

#### 根拠

- 改善が確認できない（全KPI 有意差なし）
- スコア膨張という副作用がある
- P12 が機能しない構造的原因は「shortage が P12 を上回って支配」であり、shortage が解消されない限り P12 による選択差異は生まれない

#### 今後の方針（実測根拠）

shortage（P4）が支配的な現状では、scoreShifts への学習データ追加はいずれも機能しない。
**修正セル削減のために今後取り組むべきは「shortage 削減」であり、遷移確率ではない。**

Step6-B の P12 実装は App.jsx から削除する（revert コミット）。
