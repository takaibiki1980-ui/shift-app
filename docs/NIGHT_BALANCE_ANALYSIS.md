# Phase5 Step2 原因分析レポート
## 「旧アルゴリズムが高い夜勤回数均等性を実現する理由とv1〜v3の失敗原因」

作成日: 2026-06-29  
対象: kaigo1 / kaigo2 夜勤配置アルゴリズム  
ソース: App.jsx ステップ2 (L1132〜), 4パターン100試行シミュレーション

---

## 1. 旧アルゴリズムが高性能な理由

### 1-1. コード構造（旧アルゴリズム ステップ2）

```javascript
.sort((a, b) =>
  Object.values(res[a.id]).filter(v => v === "夜勤").length -
  Object.values(res[b.id]).filter(v => v === "夜勤").length
)
```

**比較キーは夜勤回数の1つのみ**。二次キー・三次キーなし。

### 1-2. なぜこれが「夜勤回数均等」を実現するのか

JavaScriptの `Array.sort()` は **stable sort**（V8エンジン / Node.js 11+保証）。

- 夜勤回数が同じスタッフ間では、**元の配列順（nightPool配列順）が保持される**
- nightPool は `ds.filter(s => s.nightOk && _nightAllowed(s))` の出力 → **毎回固定の配列順**
- 結果として: **「count昇順 + 同順はroster順」= 自然なラウンドロビン（循環）**

**シミュレーション検証（制約なし、5名、30日）**:

```
配置順: d1:S0 d2:S1 d3:S2 d4:S3 d5:S4  ← 1周目
        d6:S0 d7:S1 d8:S2 d9:S3 d10:S4 ← 2周目
        ...（6周 × 5名 = 30日）
結果: 全員 total=6, σ=0.000
```

完全なラウンドロビンが自動的に成立する。

### 1-3. kaigo1が特に優秀な数学的理由

| 項目 | kaigo1 |
|------|--------|
| nightPool規模 | 5名 (nightOk: indices 0,1,3,5,7) |
| 月間日数 | 30日 |
| minStaff["夜勤"] | 1名/日 |
| 総夜勤配置数 | 30回 |
| 1名あたり | 30 ÷ 5 = **6.0回（ちょうど割り切れる）** |
| autoMax | ceil(30/5) = 6 |

- `totalNights % nightPoolSize === 0` → 完全均等が数学的に可能
- autoMax = 理想回数 = 6 → 全員が上限ちょうどで収まる
- 制約（canNight）が少ない試行では σ=0.000 が実現される

kaigo2は制約・スタッフ構成が複雑なため旧アルゴリズムでも σ=0.078 と高め。

### 1-4. stable sortが均等を実現するメカニズム

```
Day 1: counts=[0,0,0,0,0] → sort → [S0,S1,S2,S3,S4] → S0選択 → counts=[1,0,0,0,0]
Day 2: counts=[1,0,0,0,0] → sort → [S1,S2,S3,S4,S0] → S1選択 → counts=[1,1,0,0,0]
Day 3: counts=[1,1,0,0,0] → sort → [S2,S3,S4,S0,S1] → S2選択 → counts=[1,1,1,0,0]
...
```

各日において「count最小のスタッフ」が選ばれ、同count内はroster順が保たれる。
これはcircular queueと等価であり、1周=N日の完全均等サイクルを形成する。

## 2. v1〜v3が悪化した本当の原因

### 2-1. v1（多因子スコア）の失敗

```javascript
// nightScore = 3.0*remainSlots + 2.0*intervalBonus + 1.0*posBonus
```

**問題**: `posBonus`（idealNext日との近さ）が roster順ラウンドロビンを破壊。

- idealNextは各スタッフの「前回夜勤日 + 理想間隔」に基づいて計算
- 同count内でposBonus順にソートされると、元のroster順が崩れる
- **循環キューが壊れる** → 特定スタッフが連続して選ばれる日 / 選ばれない日が生じる

検証結果: kaigo1 σ 0.037→0.107 (+187%, p<0.05)

### 2-2. v2（優先順位型 + posBonus）の失敗

```javascript
// ① count → ② intervalTier → ③ posBonus
```

**v1と実質的に同一**。理由:

- v1の重み比: `3.0×1 = 3.0` vs 最大(interval+pos) = `2.0×1.0 + 1.0×1.0 = 3.0`
- count差が1のとき、v1はcount側が必ず勝つ
- v2も①countが変わらない限り②以降の順序は同じ
- **両アルゴリズムは同一結果を出力** → 検証結果も完全一致（σ=0.107で等値）

### 2-3. v3（halfCount secondary）の課題

```javascript
// ① count → ② halfCount → ③ lastNightDay（ascending）
```

**設計は正しいが、微小な副作用がある**:

- 「count均等なのに半月内で夜勤が偏ったスタッフ」を後回しにする
- この操作が**roster順ラウンドロビンを僅かに乱す**
- 乱れは確率的で累積しないため影響は軽微（t=0.592, n.s.）

しかし前半後半偏差は **-53% (p<0.01)** の大幅改善を実現。

### 2-4. 前半後半偏差の真の原因（重要発見）

シミュレーションと理論分析により判明:

**前半後半偏差の主因はステップ2の比較関数ではなく、ステップ1.5アンカー配置。**

```
ステップ1.5: kiboByMonth希望休D → D-2夜勤, D-1明け を先行固定
→ 希望休が前半に集中する試行 → 前半夜勤過多
→ 希望休が後半に集中する試行 → 後半夜勤過多
```

旧アルゴリズムのステップ2は「残余配置」を担うが、アンカーで生じた偏りを
**能動的に補正する機能を持たない**（count-onlyのため）。

v3のhalfCount二次キーは「残余配置の段階でアンカー偏りを補正しようとする」機能であり、
これが -53% 改善の本体。

## 3. 比較関数だけで改善可能か

### 結論: **部分的には可能、しかし根本解決にならない**

比較関数で制御できる範囲:
- ✅ 残余配置（アンカー後の日々の夜勤割当）の均等化
- ✅ count equity（ラウンドロビン維持）
- ✅ 間隔の均等化（lastNightDay活用）

比較関数で制御できない範囲:
- ❌ アンカー配置(Step1.5)自体の前後半偏り
- ❌ アンカー配置後の偏りの後処理的補正（比較関数は前向き選択のみ）
- ❌ G-1/NG-2制約が発動した際の配置順変更による偏り補正

v3の halfCount 二次キーはこの限界の中で最大限の効果（-53%）を発揮している。
count equityへの副作用（σ: 0.037→0.050）は統計的に有意でない（t=0.592, p=n.s.）。

## 4. アルゴリズム全体の見直しが必要か

### 必要な背景情報

| 旧アルゴリズムKPI | 実測値（n=100 kaigo1） |
|---|---|
| 夜勤回数σ | 0.037（ほぼ完璧） |
| 前半後半偏差mean | **0.854**（大きな課題） |
| 夜勤間隔σ | 1.216 |

前半後半偏差の主因がアンカー配置にあるとすれば、次の2つのアプローチが考えられる。

### アプローチA: ステップ2比較関数の改良（v3の改善）

v3は前半後半偏差を-53%改善し、count equityへの影響はn.s.。
strictな採用判定（すべての指標が改善方向）をどう扱うかが焦点。

**メリット**: 変更範囲が最小限  
**限界**: アンカー起因の偏りへの対処は残余配置の均等化のみ

### アプローチB: ステップ1.5アンカー配置の前後半均等化

アンカー処理自体に「前後半バランスチェック」を追加する。

```
例: 希望休が前半に集中するスタッフにアンカーを適用する際、
    既にそのスタッフが前半夜勤2回以上なら抑制する
```

**メリット**: 偏差の発生源を絶つ → 最大効果  
**デメリット**: アンカー配置の変更は禁止対象（PassA変更に準ずる可能性）

### アプローチC: ステップ2後にswap最適化パスを追加

全配置完了後、「前半過多スタッフA」と「後半過多スタッフB」の夜勤日をswapする。

```
条件: swap後にcanNight制約を満たすこと
効果: count変化なし、前後半偏差のみ改善
```

**メリット**: count equityを完全に保ちながら前後半偏差を補正できる  
**デメリット**: swap候補探索のロジックが複雑、テストコストが高い

## 最終回答

### ① 問題の本質は比較関数か

**部分的にyes、しかし全体的にno。**

比較関数（ステップ2ソート）は「残余配置の選択順」を決定するだけ。
前半後半偏差の主因はステップ1.5アンカー配置の偶発的前後半分布にある。
比較関数での改善は「被害を局所的に補正する」操作であり、原因の除去ではない。

### ② 問題の本質は配置アルゴリズム（全体構造）か

**yes。** アンカー配置（ステップ1.5）→ ステップ2 という2段構成が前後半偏差を構造的に生む。
ステップ1.5でアンカーが前半に集中すると、ステップ2がどんな比較関数でも補正は困難。

### ③ v4以降の比較関数改善に見込みはあるか

**ない。** v3はステップ2比較関数として得られる最大効果をほぼ達成している。
これ以上の比較関数改善は「既に限界を実証した枠組みの中で試行錯誤を続ける」ことになる。

### ④ Step2を再設計すべきか

**Step2（比較関数改善）は「調査・検証完了」として終了する。**

次の改善はアンカー配置（ステップ1.5）の改善（Phase5 Step3）へ移行する。
